YSFX VS NILAMP PERFORMANCE COMPARISON
=====================================

Date: 2026-05-10
Native commit tested after GUI idle redraw fix: 91be464


SUMMARY
-------

The current full audio-only benchmark harness uses unity input feed for both
nilamp and YSFX, matching DAW-hosted YSFX behavior. It shows nilamp native
CLAP/VST3 processing at about 2x the throughput of Keller's JSFX running under
ysfx:

    Surface        Median ns/frame  Median realtime factor
    -------------  ---------------  ----------------------
    Keller/ysfx             941.11                   22.14x
    nilamp CLAP             454.10                   45.88x
    nilamp VST3             456.84                   45.60x

    Matched-condition median speedup:
        nilamp CLAP vs Keller/ysfx:  2.08x
        nilamp VST3 vs Keller/ysfx:  2.06x

A parity run measured native/JSFX output peaks of 0.3422 / 0.3422 and best
gain of +0.00 dB, addressing Keller's reported approximately 6 dB lower nilamp
input level.

The Reaper realtime performance meter shows a smaller but still favorable
host-visible difference:

    nilamp VST3 peak CPU:       about 0.58%
    Keller JSFX via ysfx peak:  about 0.78%
    Relative reduction:         about 25.6%

These measurements are not contradictory. The harness isolates plugin audio
processing. Reaper's realtime meter includes host scheduling, wrapper overhead,
editor/UI behavior when the editor is open, and other DAW-side costs.

Overall conclusion:

    For raw audio processing, nilamp native CLAP/VST3 is consistently about 2x
    faster than Keller's JSFX under ysfx on this machine. In a real DAW meter,
    the observed advantage is smaller but still favorable: nilamp VST3 was
    about 25.6% lower peak CPU in REAPER. Keller's Gig Performer observation
    is therefore more consistent with host/editor accounting and the previous
    6 dB calibration mismatch than with the native DSP being slower than YSFX.


TEST MACHINE
------------

Local hardware and OS context for these measurements:

    CPU:              AMD Ryzen 9 7950X3D 16-Core Processor
    Cores / threads:  16 cores / 32 threads
    Max boost:        about 5.76 GHz, boost enabled
    CPU governor:     performance
    Scaling driver:   amd-pstate-epp
    L3 cache:         128 MiB across 2 instances
    Memory:           61 GiB total, about 51 GiB available during check
    Swap:             61 GiB configured, effectively unused during check
    GPU:              AMD Radeon RX 7900-series / Navi 31
    OS/kernel:        CachyOS Linux 7.0.5-2-cachyos, PREEMPT_DYNAMIC

Interpretation:

    The audio-only harness is effectively a single-thread throughput test. Its
    near-100% CPU readings mean the benchmark worker is saturating one CPU
    thread while running as fast as possible, not that the full 32-thread
    system is loaded.

    The Reaper peak CPU readings are small in absolute terms because this is a
    high-end desktop CPU. The relative difference is the useful signal:
    nilamp VST3 was about 25.6% lower than Keller JSFX via ysfx in this Reaper
    test.

    Memory is not a bottleneck for these measurements. Plugin and harness
    footprints are tiny relative to the installed RAM.

    The 7950X3D's dual-CCD design can introduce some run-to-run variation
    depending on scheduler placement, but same-session nilamp-vs-ysfx
    comparisons remain meaningful.


REAPER REALTIME OBSERVATION
---------------------------

Environment:

    Host:        REAPER
    Measurement: REAPER Performance Meter, realtime playback
    Compared:    nilamp VST3 vs Keller JSFX loaded through ysfx

Observed peak CPU:

    Surface                 Peak CPU
    ----------------------  --------
    nilamp VST3              0.58%
    Keller JSFX via ysfx     0.78%

Derived comparison:

    Difference:              0.20 percentage points
    Relative reduction:      (0.78 - 0.58) / 0.78 = 25.6%

Interpretation:

    nilamp VST3 is lower in REAPER's host-visible realtime meter, but not by
    the same factor as the isolated audio benchmark. This is expected because a
    DAW meter includes work outside the raw DSP loop.

    Keller's Gig Performer report of native VST3 being similar or slightly
    higher than ysfx may have been influenced by editor/GUI cost, host meter
    accounting, or host-specific plugin scheduling. The nilamp GUI now avoids
    continuous idle redraws while keeping the editor event pump responsive.

Native-vs-YSFX output residual sanity:

    Median RMS(native output - YSFX output) vs Keller peak:  -77.2 dB
    Range observed:                                        -109.0 dB to -23.2 dB

This is not an input-to-output noise-floor measurement. It is the RMS
difference between nilamp native output and Keller/YSFX output, after the
benchmark trims the first 100 ms warm-up window, normalized against the peak
Keller/YSFX output for that condition. The residual range varies by input/case
because the harness covers both linear and nonlinear settings. The benchmark is
for performance; the ABX/parity tests remain the public behavior gate.


LIFECYCLE AND RELOAD
--------------------

Median warm-path lifecycle/reload timings from the same harness:

    Phase             Surface        Median wall time
    ----------------  -------------  ----------------
    plugin_lifecycle  Keller/ysfx             8.53 ms
    plugin_lifecycle  nilamp CLAP             0.70 ms
    plugin_lifecycle  nilamp VST3             0.002 ms
    reload            Keller/ysfx             8.55 ms
    reload            nilamp CLAP             0.69 ms
    reload            nilamp VST3             0.002 ms

Notes:

    Keller/ysfx lifecycle and reload include JSFX load/compile/JIT behavior.

    The VST3 lifecycle/reload numbers are warm-path measurements inside one
    process and can retain SDK/module state. They are useful for regression
    spotting, but cold VST3 startup should be checked in a real host or a
    subprocess-based driver.
