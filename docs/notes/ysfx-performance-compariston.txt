YSFX VS NILAMP PERFORMANCE COMPARISON
=====================================

Updated: 2026-05-11


SUMMARY
-------

I measured nilamp against Keller's TWD DLX II JSFX in two different ways.
They answer different questions.

The command-line benchmark, run on Linux, measures audio processing only. It
loads Keller's JSFX under headless ysfx, loads nilamp as CLAP and VST3, warms
the effects, and then times in-memory processing blocks. It excludes REAPER,
plugin editors, host scheduling, meters, graphics, and UI event processing.

That benchmark shows nilamp processing about twice as fast as Keller's JSFX
under ysfx:

    Surface        Median ns/frame  Median realtime factor
    -------------  ---------------  ----------------------
    Keller/ysfx             941.11                   22.14x
    nilamp CLAP             454.10                   45.88x
    nilamp VST3             456.84                   45.60x

    Matched-condition median speedup:
        nilamp CLAP vs Keller/ysfx:  2.08x
        nilamp VST3 vs Keller/ysfx:  2.06x

The REAPER benchmark, run on macOS, measures host-visible process CPU. It
plays a recorded guitar track in REAPER with nilamp CLAP, nilamp VST3, and
Keller's JSFX under ysfx in the track FX chain. A ReaScript enables one amp
format at a time and switches between editor-closed and editor-open states. A
Python sampler records REAPER process CPU.

The macOS REAPER run shows nilamp CLAP and VST3 both below Keller/ysfx:

    Scenario                   Median CPU  p95 CPU
    -------------------------  ----------  -------
    Keller/ysfx, editor closed     1.958%   2.539%
    Keller/ysfx, editor open       2.867%   3.358%
    nilamp CLAP, editor closed     1.208%   1.665%
    nilamp CLAP, editor open       1.317%   1.807%
    nilamp VST3, editor closed     1.600%   2.149%
    nilamp VST3, editor open       1.742%   2.250%

CLAP used about 1.62x less median process CPU than Keller/ysfx with the editor
closed and 2.18x less with the editor open. VST3 used about 1.22x less median
process CPU with the editor closed and 1.65x less with the editor open.

These results are not contradictory. The Linux command-line benchmark isolates
raw audio processing. The REAPER benchmark includes the host, plugin wrappers,
windows, transport, scheduling, and whatever REAPER itself does while playing.
The command-line result is the better DSP-throughput measurement. The REAPER
result is the better "what does the DAW see?" measurement.


REAPER CPU MEASUREMENT FILES
----------------------------

The REAPER numbers come from a scripted macOS run:

    Summary JSON:
        dist/reaper-perf/reaper-cpu-summary-20260511-131909.json

    Raw samples:
        dist/reaper-perf/reaper-cpu-samples-20260511-131909.json

    Scenario markers:
        dist/reaper-perf/reaper-markers-20260511-131909.json

The sampler records host-visible REAPER process CPU using `ps` samples. It
does not scrape REAPER's "CPU" or "FX CPU" Performance Meter values. REAPER
exposes good scripting control for FX windows and playback, but not a stable
public API for reading those meter values. For FX-only cost, use the
command-line benchmark instead.

    Median RMS(native output - YSFX output) vs Keller peak:  -77.2 dB

This is not an input-to-output noise-floor measurement. It is the RMS

the first 100 ms warm-up window, normalized against the peak Keller/YSFX output
for that condition. The residual range varies because the matrix includes both
linear and nonlinear settings.


MACOS REAPER HOST-VISIBLE CPU BENCHMARK
---------------------------------------

Source:

    dist/reaper-perf/reaper-cpu-summary-20260511-131909.json

Host:

    REAPER on macOS

Project:

    One recorded guitar track with all three FX in the track FX chain.

    Compared FX:       nilamp CLAP, nilamp VST3, HK TWD DLX II JSFX under ysfx

Method:

    1. Start REAPER with the guitar project open.
    2. Start tools/reaper_perf/measure_reaper_cpu.py.
    3. Run tools/reaper_perf/run_reaper_perf_scenarios.lua from REAPER.
    4. The ReaScript runs three passes of six scenarios:
           nilamp CLAP, editor closed
           nilamp CLAP, editor open
           nilamp VST3, editor closed
           nilamp VST3, editor open
           Keller JSFX under ysfx, editor closed
           Keller JSFX under ysfx, editor open
    5. The script enables one amp format at a time on the same track and
       restores the original state when done.
    6. The Python sampler records REAPER process CPU every 250 ms.

Aggregate results, normalized to total logical CPU capacity:

    Scenario                   Samples  Mean CPU  Median CPU  p95 CPU  Max CPU
    -------------------------  -------  --------  ----------  -------  -------
    Keller/ysfx, editor closed     304    2.037%      1.958%   2.539%   2.683%
    Keller/ysfx, editor open       304    2.926%      2.867%   3.358%   3.492%
    nilamp CLAP, editor closed     304    1.251%      1.208%   1.665%   1.800%
    nilamp CLAP, editor open       304    1.366%      1.317%   1.807%   1.958%
    nilamp VST3, editor closed     303    1.690%      1.600%   2.149%   2.742%
    nilamp VST3, editor open       305    1.788%      1.742%   2.250%   2.375%

Median process-CPU comparison against Keller/ysfx:

    Editor closed:
        Keller/ysfx median:  1.958%
        nilamp CLAP median:  1.208%  (1.62x lower)
        nilamp VST3 median:  1.600%  (1.22x lower)

    Editor open:
        Keller/ysfx median:  2.867%
        nilamp CLAP median:  1.317%  (2.18x lower)
        nilamp VST3 median:  1.742%  (1.65x lower)

This macOS REAPER run supports the command-line result directionally: native
CLAP/VST3 both use less host-visible process CPU than Keller/ysfx, with CLAP
showing the largest margin in this project.


LIFECYCLE AND RELOAD
--------------------

The command-line benchmark also reports warm-path lifecycle/reload timings:

    Phase             Surface        Median wall time
    ----------------  -------------  ----------------
    plugin_lifecycle  Keller/ysfx             8.53 ms
    plugin_lifecycle  nilamp CLAP             0.70 ms
    plugin_lifecycle  nilamp VST3             0.002 ms
    reload            Keller/ysfx             8.55 ms
    reload            nilamp CLAP             0.69 ms
    reload            nilamp VST3             0.002 ms

Keller/ysfx lifecycle and reload include JSFX load/compile/JIT behavior. The
VST3 lifecycle/reload numbers are warm-path measurements inside one process, so
they are useful for regression checks but not for a cold-start DAW claim.


CONCLUSION
----------

For isolated audio processing, nilamp native CLAP/VST3 is about twice as fast
as Keller's JSFX under ysfx on this machine.

Inside REAPER, the difference is much smaller because REAPER measures a larger
system: the DAW, transport, wrappers, editor windows, and scheduling. In the
scripted macOS REAPER run, nilamp CLAP and VST3 both used less median process
CPU than Keller's JSFX under ysfx.

The cleanest summary is:

    Audio-only command-line benchmark:
        nilamp is about 2x faster.

    REAPER host-visible benchmark:
        nilamp is lower than Keller/ysfx, with CLAP showing the largest margin.

That is the expected shape. Raw DSP improvements show up strongly in an
isolated harness. In a real DAW, host and UI costs dilute the difference, but
the current macOS REAPER run still favors native CLAP/VST3 over Keller/ysfx.
