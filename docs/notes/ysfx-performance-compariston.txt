YSFX VS NILAMP PERFORMANCE COMPARISON
=====================================

Updated: 2026-05-10


SUMMARY
-------

I measured nilamp against Keller's TWD DLX II JSFX in two different ways.
They answer different questions.

The command-line benchmark, run on Linux, measures audio processing only. It
loads Keller's JSFX under headless ysfx, loads nilamp as CLAP and VST3, warms
the effects, and then times in-memory processing blocks. It excludes REAPER,
plugin editors, host scheduling, meters, graphics, and UI event processing.

That benchmark shows nilamp processing about twice as fast as Keller's JSFX
under ysfx:

    Surface        Median ns/frame  Median realtime factor
    -------------  ---------------  ----------------------
    Keller/ysfx             941.11                   22.14x
    nilamp CLAP             454.10                   45.88x
    nilamp VST3             456.84                   45.60x

    Matched-condition median speedup:
        nilamp CLAP vs Keller/ysfx:  2.08x
        nilamp VST3 vs Keller/ysfx:  2.06x

The REAPER benchmark, run on Windows, measures host-visible process CPU. It
plays a recorded mono DI part in REAPER 7.71. A ReaScript switches between
nilamp VST3 and Keller's JSFX on the same track. A PowerShell sampler records
REAPER process CPU while the editor is closed and open.

The REAPER run shows median host CPU essentially tied. The p95 values favor
nilamp, especially with the editor open:

    Scenario                   Median CPU  p95 CPU  Max CPU
    -------------------------  ----------  -------  -------
    Keller/ysfx, editor closed     0.192%   1.392%   4.208%
    Keller/ysfx, editor open       0.193%   1.467%   4.240%
    nilamp VST3, editor closed     0.192%   1.282%   3.282%
    nilamp VST3, editor open       0.192%   0.958%   3.858%

In this REAPER run, nilamp VST3 was not more expensive than Keller JSFX. The
median values are too close to call. At p95, nilamp was about 7.9% lower with
the editor closed and about 34.7% lower with the editor open.

These results are not contradictory. The Linux benchmark isolates raw audio
processing. The REAPER benchmark includes the host, the plugin wrapper, editor
windows, transport, scheduling, and whatever REAPER itself does while playing.
The command-line result is the better DSP-throughput measurement. The REAPER
result is the better "what does the DAW see?" measurement.

----------------------------

The REAPER numbers come from a scripted run:

    Raw samples:
        dist/reaper-perf/reaper-cpu-samples-20260510-211724.json

    Scenario markers:
        dist/reaper-perf/reaper-markers-20260510-211724.json

The sampler records REAPER process CPU from Windows process time deltas. It
does not scrape REAPER's "CPU" or "FX CPU" meters. REAPER exposes good scripting
control for FX windows and playback, but not a stable public API for reading
those Performance Meter values. For FX-only cost, I use the command-line
benchmark instead.

REAPER HOST-VISIBLE CPU BENCHMARK
---------------------------------

Source:

    dist/reaper-perf/reaper-cpu-summary-20260510-211724.json

Host:

    REAPER 7.71 on Windows

Project:

    C:\Users\mag\Documents\REAPER Media\nilamp.rpp

    Sample rate:       44100 Hz
    Input item:        Media\01-260510_2114.wav
    Input format:      mono 24-bit PCM WAV
    Compared FX:       nilamp VST3 vs HK/TWD DLX II.jsfx
    Disabled FX:       nilamp CLAP bypassed

Method:

    1. Start REAPER with the saved comparison project.
    2. Start tools/reaper_perf/measure_reaper_cpu.ps1.
    3. Run tools/reaper_perf/run_reaper_perf_scenarios.lua from REAPER.
    4. The ReaScript runs three passes of four scenarios:
           nilamp VST3, editor closed
           nilamp VST3, editor open
           Keller JSFX under ysfx, editor closed
           Keller JSFX under ysfx, editor open
    5. The script enables one amp at a time on the same track and restores the
       original state when done.
    6. The PowerShell sampler records REAPER process CPU every 250 ms.

Each scenario uses about 30 seconds of measurement. The sampler trims the first
2 seconds and the last 1 second from each scenario before summarizing. The
aggregate rows below combine the three passes.

Aggregate results, normalized to total logical CPU capacity:

    Scenario                   Samples  Mean CPU  Median CPU  p95 CPU  Max CPU
    -------------------------  -------  --------  ----------  -------  -------
    Keller/ysfx, editor closed     317    0.335%      0.192%   1.392%   4.208%
    Keller/ysfx, editor open       313    0.430%      0.193%   1.467%   4.240%
    nilamp VST3, editor closed     315    0.337%      0.192%   1.282%   3.282%
    nilamp VST3, editor open       315    0.327%      0.192%   0.958%   3.858%

The medians are effectively the same. They sit around 0.192% of total machine
CPU in all four scenarios. That is too small a difference to use as a ranking.

The p95 values are more useful because they show the upper part of the normal
run, without giving all the weight to a single maximum sample:

    Editor closed:
        Keller/ysfx p95:   1.392%
        nilamp VST3 p95:   1.282%
        nilamp reduction:  7.9%

    Editor open:
        Keller/ysfx p95:   1.467%
        nilamp VST3 p95:   0.958%
        nilamp reduction:  34.7%

This Windows REAPER run does not support the idea that nilamp VST3 is heavier
than Keller's JSFX under ysfx. With the editor closed, the two are very close.
With the editor open, nilamp's p95 process CPU is lower in this run.


LIFECYCLE AND RELOAD
--------------------

The command-line benchmark also reports warm-path lifecycle/reload timings:

    Phase             Surface        Median wall time
    ----------------  -------------  ----------------
    plugin_lifecycle  Keller/ysfx             8.53 ms
    plugin_lifecycle  nilamp CLAP             0.70 ms
    plugin_lifecycle  nilamp VST3             0.002 ms
    reload            Keller/ysfx             8.55 ms
    reload            nilamp CLAP             0.69 ms
    reload            nilamp VST3             0.002 ms

Keller/ysfx lifecycle and reload include JSFX load/compile/JIT behavior. The
VST3 lifecycle/reload numbers are warm-path measurements inside one process, so
they are useful for regression checks but not for a cold-start DAW claim.


CONCLUSION
----------

For isolated audio processing, nilamp native CLAP/VST3 is about twice as fast
as Keller's JSFX under ysfx on this machine.

Inside REAPER, the difference is much smaller because REAPER measures a larger
system: the DAW, transport, wrappers, editor windows, and scheduling. In the
scripted Windows REAPER run, median process CPU was tied, and nilamp VST3 had
lower p95 CPU than Keller's JSFX under ysfx.

The cleanest summary is:

    Audio-only command-line benchmark:
        nilamp is about 2x faster.

    REAPER host-visible benchmark:
        median CPU is tied; p95 favors nilamp in this run.

That is the expected shape. Raw DSP improvements show up strongly in an
isolated harness. In a real DAW, the host and UI costs dilute the difference.
