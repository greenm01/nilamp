# AGENTS.md — guide for AI coding agents

This file documents project conventions, hot zones, build mechanics, and
gotchas for agents working on `nilamp`. Humans should read `README.md` first;
this file adds the operational details an agent needs to act safely.

## Working rules

1. Think before coding. State assumptions, surface tradeoffs, and ask when
   intent is genuinely ambiguous.
2. Keep changes simple. Do not add speculative features, abstractions, or
   configurability.
3. Make surgical edits. Touch only files needed for the request and clean up
   only the mess your change creates.
4. Define verification. Turn every bugfix or feature into concrete checks and
   run them before finishing when feasible.

## TL;DR

- **Language stack**: C for realtime DSP and offline rendering. Lua may be
  used for build-time config/codegen only. Python remains the numerical
  oracle, fixture generator, and ABX analysis layer.
- **Reference behaviour**: Helmut Keller's JSFX implementations under
  `vendor/keller-jsfx/` and the staged JSFX harness are canonical.
- **Build system**: plain `make`.
- **Current deliverable**: native offline renderer, tests, and a no-GUI C CLAP
  plugin shell at `native/bin/nilamp.clap`.
- **Do not edit JSFX harness files** in `~/.config/REAPER/...`; that
  invalidates cached A-channel renders used by ABX comparisons.
- **Read `docs/next-session.md` first.** It is most-recent-first and records
  the live investigation state.

## Build mechanics

Use plain make:

```bash
make native
make native-test
make clean-native
```

`make native` builds:

- `native/bin/nilamp_render`
- `native/bin/nilamp_taps_render`
- `native/bin/nilamp.clap`
- `native/bin/test_native`
- `native/bin/test_clap_load`

`native/generated/nilamp_tables.c` and `.h` are generated by:

```bash
python3 tools/gen_5e3_tables.py
```

The normal native build consumes those generated C files directly. It must not
depend on legacy DSP source formats or generated build output.

## C conventions

- C11, compiled with `-Wall -Wextra -Wpedantic -Werror`.
- No allocation, file I/O, locks, Lua, Python, or host calls in future realtime
  audio processing.
- `native/src/nilamp_clap.c` may allocate only outside `process()`
  (`create_plugin`/`activate`/`deactivate`/`destroy`). Keep `process()` free of
  allocation, locks, file I/O, Lua/Python, and host callbacks.
- Keep DSP state explicit in structs. Sample ordering matters; prefer a
  readable per-sample function over clever graph abstractions.
- The 5E3 PSS order must match JSFX:
  previous-sample tube currents feed PSS first, then current-sample `dvs2` and
  `dvs3` feed the tube stages in the same sample.
- If porting a JSFX block, cite the JSFX source/line range in a comment when
  that helps mechanical verification.

## Lua and Python

- Lua is for build-time config/codegen only. It must not run in the renderer,
  plugin, or audio callback.
- Python is allowed for numerical generation and reference analysis.
- `tools/keller_oracle.py` is the numerical reference. Changing it invalidates
  fixtures; regenerate fixtures and rerun native tests after oracle changes.
- Fixtures are raw little-endian `f32` files consumed by native tests.

## Hot zones

- `native/src/nilamp_dsp.c` — production DSP and the JSFX-order PSS/tube loop.
- `native/generated/nilamp_tables.c` — generated ADNL data; update through
  `tools/gen_5e3_tables.py`, never by hand.
- `tools/keller_oracle.py` and `tools/gen_5e3_tables.py` — numeric source of
  truth for fixtures and tables.
- `tools/abx_compare.py` — public JSFX-vs-native gate.
- `~/.config/REAPER/Effects/nilamp_abx/*.jsfx*` — do not edit.

## Reference-checking workflow

When making DSP-affecting changes:

1. State the hypothesis in one sentence.
2. Make the smallest possible C/Python/Lua change.
3. Run `make native-test`.
4. If the change affects full-pipeline behavior, run `make native` and ABX via
   `python3 tools/abx_compare.py`.
5. Public gate: sine residual >= `-16 dB`, sweep residual >= `-11.2 dB`.
6. Record the result at the top of `docs/next-session.md`.
7. Commit with a message that captures why the change exists.

## When in doubt

1. Read `docs/next-session.md`.
2. Check Keller's JSFX source under `vendor/keller-jsfx/`.
3. Compare against `tools/keller_oracle.py`.
4. Ask before reverting prior investigative work that is not obviously yours.
